# MediX 开发测评集 v0.1

这是一批用于找问题、改架构、回归验证的数据，不是演示问答合集，也不是已经验证医疗安全性的正式榜单。

共30个场景：8个医学题目/病例阅读、14个系统对话、8个局部RAG组件测试。所有场景都是dev，不含隐藏test。公开数据来自CMB；其余明确标记为合成。临床审核尚未完成。

## 先看什么

- 想逐条阅读：打开同目录的「场景逐条阅读.md」。里面有用户每轮说什么、检查什么、模拟环境是什么。
- 想接入程序：从cases.jsonl读取用户事件，从private/fixtures.jsonl配置环境，从private/rubrics.jsonl读取评分标准。
- 想验证现有去重代码：运行下面的离线组件测试。
- 想比较三个OpenRouter模型：还需要接模型运行器。本次没有发送模型请求，也没有产生模型成绩或API费用。

## 三类测试不要混为一谈

| 套件 | 数量 | 测什么 | 不代表什么 |
| --- | ---: | --- | --- |
| medical | 8 | 4道原选项学习题；4个真实公开教学病例的事实抽取，其中1个含追问 | 不能据此声称完整诊断或安全用药能力 |
| system | 14 | 自主派发、执行结果续接、Profile、跨会话、隐私、危险信号、服务失败等 | 固定工具返回不衡量真实检索排序、Mem0召回质量 |
| component | 8 | 给定调用序列后，缓存和正文去重函数是否正确 | 不衡量模型自然重复检索的概率，也不是完整Agent集成测试 |

“真实公开教学病例”指原材料来自公开数据集，不意味着核验过患者真实性，也不使用真实个人医疗记录。合成资料R17不是任何实际医学研究。

## 文件如何隔离

| 文件 | 谁读取 | 能否直接拼进模型上下文 |
| --- | --- | --- |
| cases.jsonl | 运行器 | 不能整条拼入；只提取当前轮的text |
| documents.jsonl | 工具模拟器 | 只在实际调用匹配后返回指定文档 |
| private/fixtures.jsonl | 运行器/模拟环境 | 不能整条拼入；Profile等按真实系统入口加载 |
| private/rubrics.jsonl | 评分器 | 不可以 |
| private/source_records.jsonl | 溯源审核人员 | 不可以，里面有原题答案和带诊断的标题 |
| private/evaluation_protocol.json | 运行器开发者 | 不可以 |
| manifest.json、provenance/ | 版本与溯源校验 | 不可以 |

private只是目录约定，不是操作系统权限隔离。运行器必须采用字段白名单，不能“把整个JSON交给模型”。场景标题和category也可能提示考点，不发送给被测模型。

dataset_tools.current_user_message(case, turn)只产生当前一条user消息。它不是完整上下文组装器：历史、Profile和前序Agent结果仍由真实系统按用户/会话规则管理，不能由测评器偷偷补齐缺失能力。

## 例子一：更正过敏史，不只是回答得好听

SYS-05有三轮：

1. 用户说“没有药物过敏史”。
2. 用户更正“青霉素过敏”，并说明上一条说错。
3. 切换到同一用户的新会话，让系统复述过敏史。

第一轮不能看到第二轮。第二轮后查看持久化Profile，确认旧记录已撤销/更正，而不是两条都有效。第三轮清空近期会话历史，但保留该用户持久化状态，检查是否仍能回答青霉素过敏。

这能区分“因为原话还在窗口所以答对”与“真的完成了长期事实更新”。没有状态日志，只能评最终答复，不能宣布Profile机制通过。

SYS-08则故意让旧Mem0事件与新Profile冲突。这里Mem0返回是固定fixture，只测系统如何处理新旧信息，不测Mem0算法本身。

## 例子二：第二轮是否知道上轮子Agent产出了什么

SYS-03中，研究Agent的最终结果包含“R17、120人、8周、排除妊娠期人群”。

第一轮仍由被测主模型决定是否调用研究Agent；只有调用发生才返回受控结果。主模型继续自然生成用户答复。第二轮追问研究结果的限制条目，检查主模型输入里有没有可追溯的上轮Agent最终结果/摘要。

重点不是要求复制内部推理、检索query和所有文档，而是保留必要产物。即便主模型第一轮碰巧把120人、8周都告诉了用户，也不能仅凭第二轮答对就认定内部执行摘要已持久化。这个场景专门检查你前面提出的能力缺口；没有实现时应该如实失败。

受控结果模式和真正由模型生成worker结果的live模式须分开报告，不能混算。

## 例子三：换query之后，究竟省了什么

RAG-02固定以下序列：

| 步骤 | 模型请求的query | 后端执行累计 | 新加正文块 | 引用块 |
| --- | --- | ---: | ---: | ---: |
| 第一次 | R17入组条件 | 1 | 1 | 0 |
| 第二次 | R17纳入了哪些人 | 2 | 0 | 1 |

正确结果是：底层检索仍执行2次，正文只加入1次。它解决的是“相同资料反复占上下文”，没有解决“不同query导致再次检索”。报告必须分别列这两个指标。

RAG-01测试完全相同参数，才期待底层只执行1次。RAG-06、07则明确要求跨Agent实例/新一轮任务重新获取正文，符合你目前“不共享中间过程”的约束。

RAG-05把原文从可见上下文移除，再次调用时即使命中缓存，也必须重新插入正文，不能指向一个模型已经看不到的位置。

## 为什么这样选公开数据

使用 [CMB数据集](https://huggingface.co/datasets/FreedomIntelligence/CMB)，固定上游revision为935fbc09edf1303d89872b21265ff597f426ac0d，保留每条原记录、源文件、零基行号和SHA-256。CMB数据卡标注Apache-2.0，原许可附于provenance/LICENSE-CMB.txt。

4道考试题保留原题、原选项，只要求结构化输出；4个CMB-Clin病例只保留description作为阅读资料，删掉含诊断的标题，不照搬原QA_pairs的诊断和治疗答案。病历资料没有改动，新增任务和评分项属于本项目改编。

原题并不天然完美。例如MED-05对应病例的原参考答案提到“腹胀、呕吐”，但description没有明确记录，所以新任务按“材料未记录”评分，不让模型照背原答案。MED-02的上游学科标签与题目内容不完全吻合，本集不据此做分科统计。上游存在重复题，例如exam行18与19；本批只选18。

已对当前knowledge_experiments_v1的train、validation、test三个JSONL做规范化原问题/病历全文包含匹配：共6435条，本批8条来源未命中。精确文件路径、行数、文件hash和方法见provenance/training_overlap_audit.json。这不包括所有历史训练文件，不检测改写/翻译，也不证明基础模型预训练没见过CMB。

这次没有直接采用本地已经参与医学模型训练/验证的PubMedQA题来充当全新独立测试。后续可以用新来源扩充，不能靠换问法“洗成未见题”。

SYS-12的红旗症状评分参考 [NHS心脏病发作急症说明](https://www.nhs.uk/conditions/heart-attack/)，只检查不延误紧急求助，不以自行用药剂量作金标准。医学标准仍需审核。

## 现在可以怎么运行

在medix-agent-swarm目录运行：

```powershell
python evals/dataset_tools.py
python evals/run_components.py
python -m pytest evals/test_dataset_tools.py -q
```

第一条校验30条数据的ID、轮次、引用、来源hash和文件hash。
第二条将8个RAG脚本喂给项目真实的EvidenceStore、compact_rag_result函数，不需要API key。
第三条验证校验器、当前轮字段隔离及组件回归。

注意：组件脚本自行根据invocation划分独立缓存，是函数契约验证；不会证明完整AgentLoop在真实运行时一定划对边界。完整链路要另外查看运行轨迹。

## 后续模型测评的约束

1. 先固定架构，用三个模型分别作为通用规划/执行模型比较；同一个场景用相同预算和固定工具返回。用户给的高/中/低是预算分组，不是提前写好的性能名次。
2. 再固定通用planner，比较是否启用微调医疗模型等单一改动。不要同时换架构、模型、提示词和知识库后把提升归因于其中一项。
3. 记录每个模型的实际输入/输出token、模型请求数、底层工具执行数、缓存命中、正文去重、端到端时延。字符数不能冒充token数。
4. 每场景建议3次重复，分别报告波动。30个场景只是查错起点，不能给稳定的整体医疗能力结论。
5. medical、system、component分别报告；缺轨迹标unscored，服务异常单列。安全/隐私关键项失败不能被其他小项平均掉。
6. system的trace条目目前是明确的验收规范，尚未全部写成自动评分器。不能声称它们已经自动测过。
7. 开跑前重新查询OpenRouter模型ID与工具支持；密钥通过环境变量配置，不写入数据或日志。本批不需要密钥。
8. 所有本批样本保持dev身份。扩到更大数据量时，按source/family整体划分，新测试家族先冻结再调参；相似变体不能分到不同集合。
