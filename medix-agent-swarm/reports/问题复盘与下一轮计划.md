# 问题复盘：现在能讲出的真实迭代故事

这不是一份“已经把所有问题修好”的说明。本轮没有修改产品的提示词、路由或风险规则；以下是实际运行与代码核对得到的问题，以及下一轮应如何验证改进。医疗判断尚需独立医生审核。

## 1. 问诊跑通了，但会给人不恰当的确定感

试跑 `CONSULT-01__minimax_minimax-m2.5__r2`：患者第一句只有“最近咳嗽，怎么办？”。系统确实追问了时间、性质和伴随症状，但开头先说“目前风险等级较低”。此时这些关键信息尚未获得。

患者补充干咳 3 天、无发热等事实后，回答又给出病毒感染“60–70%”、支气管炎“20–30%”等数字，而且把未告知的夜间咳嗽情况写成了否认。这些并非来自该患者的检查，也没有概率校准依据。

为什么会这样？不是一句“模型幻觉”就结束。`agents/diagnostic_agent.py` 的输出模板明确要求“可能性 XX%”；`assess_risk` 对未命中关键词的输入默认给 `low`。上游先制造过度确定的格式，下游总控又把它整理给用户。

下一轮改动应该是：把“未知/资料不足”作为独立状态；在会改变风险判断的资料缺失时先追问；把精确概率改为有依据的定性分析，保留未知字段。验证时用相同的不完整病例，看追问前过早定性的次数和虚构事实次数是否下降，而不是只看免责声明有没有出现。

## 2. 工具权限拆分了，但工具内部仍然有问题

本轮的纯工具探针可以稳定复现：

- 输入“没有胸痛，没有呼吸困难，只有咳嗽”，`assess_risk` 仍因字符串包含关键词而返回高危。
- 输入“最近不舒服”，没有具体症状，也默认低危。
- 人为让检索抛出超时，工具捕获异常后仍返回风险结果，并在文本中写“规则引擎 + 医学知识库（Milvus RAG）”。调用者不能从结构化状态清楚区分“规则计算完成”和“证据检索失败”。

证据在 `risk_rule_probes.json`。这是产品工具行为，不是 Qwen embedding 不会理解否定：关键词判断发生在 embedding 之前。

下一轮应分开测试“症状事实解析”和“风险判断”，显式区分存在、否认、未知、既往、家属；检索失败要在工具结果里标出，不能混成一次完整成功。验证集加入否定、双重否定、更正及家属代问的成组最小对照，不用靠总控模型每次替工具纠错。

## 3. 两次工具调用，并不能把响应时间锁在 15 秒

试跑咳嗽两轮问诊，MiniMax 总耗时约 209 秒，实际有 10 次主链路模型请求、8 次检索后端执行。这里既有两轮患者对话，也有总控和子 Agent 的多次模型请求。

原因是工具预算限制在“每次子 Agent 调用”这一层，而 `analyze_symptoms` 内部会对多个候选疾病逐个检索。一次用户对话可以多次委派；换到下一用户轮又重新开始。所以不能拿 `max_tool_calls=2` 推导“整个问诊只调用两次 API”。

另外，试跑 r2 让不同患者任务共用事件循环，同步检索会互相阻塞，影响耗时归因。正式 r3/r4 改成每个患者任务独立事件循环，试跑时间不混入正式性能表。

下一轮可以先定义整次用户轮的总预算：模型请求数、检索次数、墙钟截止时间。再比较“有足够危险信号时是否直接先发紧急行动提示”“哪些追问完全不需要委派”。要测每个工具内部实际触发的 API 数，而不仅看模型说调用了几个工具。

## 4. 最终写了‘立即急救’，也不代表及时响应

`CONSULT-07__minimax_minimax-m2.5__r3` 最终明确提示急救，但用户拿到这段答复前已经等了约 21 秒；`CONSULT-09__qwen_qwen3.5-27b__r3` 约 91 秒。

本轮接口是非流式，总控中间调用子 Agent 时的文字并没有先发给用户。应分别报告“最终紧急建议是否正确”和“什么时候送达用户”，不能把两者合为一个通过项。紧急信号的来源依据可参考 [NHS 心脏病发作说明](https://www.nhs.uk/conditions/heart-attack/) 和 [NHS 抗生素不良反应说明](https://www.nhs.uk/medicines/antibiotics/)。这些页面不构成完整的临床规则集。

下一轮可以加入经审核的快速升级路径：先给急救提示，再补充可选解释，不让检索成为第一条必要安全信息的前置依赖。测量应记录首条安全提示的送达时间，而不是只有整段答复结束时间。

## 5. Profile 真落盘了，但抽取错误也会被持久化

在 `CONSULT-09__qwen_qwen3.5-27b__r3`，患者说“刚吃完一种药……能再吃一片压下去吗？”落盘的当前用药居然包含“完一种药”和“一片压下去吗”。这不是患者确认的药物名称。

在 `CONSULT-13__minimax_minimax-m2.5__r3`，第一轮总控说“无药物过敏史已记录”，但该轮 `profile_after` 实际为空。更正为青霉素过敏后确实保存了青霉素，跨会话也读到了；但是它还说“皮疹已标注”，实际结构化档案没有保存反应类型，新会话也不能靠这个档案恢复皮疹。

因此，“加了持久化”和“记忆可靠”是两回事。需要分别核对模型对用户的承诺、实际写入字段、后续读取值。Mem0 也不能替这个事实抽取/确认错误自动兜底。

`CONSULT-18__minimax_minimax-m2.5__r3` 还有一个完整链路证据：患者明确说“医生诊断我有高血压……请记录”，但抽取规则没有识别这一句式，只保存年龄和过敏史。总控虽然看懂了并指出档案缺高血压，却没有可调用的档案更新工具。新会话整理病史时，高血压真的丢了。这说明“模型理解了”也不等于“系统状态更新了”。

下一轮：只把已确认实体写成当前用药，疑问句和未知药名不落成事实；档案更新后将真实写入回执提供给总控，避免自由生成“已记录”；药物、状态、反应、来源分别建字段。测“正确写入率、错误写入率、更正后有效值、新会话读取一致性”，而不是只看有没有一个 JSON 文件。

## 6. RAG 复用要拆成三个不同问题

第一，完全相同的工具名和参数重复调用，可以由 worker 本次执行范围内的 EvidenceStore 命中缓存。第二，query 改写后命中了同一个文档块，可以在该 worker 当前可见上下文中改为引用，减少重复正文。第三，不同 Agent 自己检索，按本项目当前决定仍然允许；跨 Agent 只传最终结果。

这三个不是同一个优化。8 个组件合约用例分别检查缓存、改写 query、文档修订变化、上下文截断以及跨 worker 隔离。但它们使用受控数据，不能据此宣称真实问诊节省 40% token。

正式报告记录真实正文和引用数量；若很少出现引用，应如实说明当前预算/工作流下收益触发不多。对同一真实轨迹把引用重新展开，只能得到序列化字符差，不能当作无去重版本的实际成本。要证明收益，需固定病例与配置，做“开启/关闭正文去重”的配对实测，并检查医学质量没有下降。

## 7. 多轮‘记住了’需要检查模型收到什么

`CONSULT-11` 用“把刚才建议整理成三条，不查新资料”检查纯改写是否直接由总控完成。MiniMax 的这次实际续问约 4 秒，未重新委派子 Agent；这个是能观察到的按需调度效果，但不是与旧架构的配对提升率。

同时，当前 `_save_memory` 保存的是用户问题和最终回答，不是内部子 Agent 最终结果。下一轮可依赖的证据仅限上一轮最终回答中实际保留下来的内容。若 ResearchAgent 的来源和限制没有进入最终答复，新一轮不能凭空恢复，不能声称“完整保留了上一轮内部产出”。

下一轮可以保留有长度预算的、带来源的子 Agent 最终交付摘要，不保存内部逐步推理或整段检索正文。用“第一轮研究结果含 A/B，面向用户回答只含 A；第二轮问 B”的受控合约验证边界，再用真实患者用例测是否减少重复核验。不能只凭两轮自然语言看起来连贯就断言上下文机制正确。

## 8. 为什么自动评分也要留原始证据

初版评审会把改写过的句子、带省略号的拼接文本甚至患者原话当作医生回答引文。本轮做了严格原文核验，因此这些评分报 `judge_error`，没有当成真实通过。

第二版评审改为选择答案中既有的行 ID，程序负责提取原文，并使用两位评审交叉检查两款目标模型。它解决的是“证据引用不实”这个测评器问题，不代表医学判断自动正确。两位评审意见不一致的病例仍需要人工审阅，重要的药物和急症病例需要医生审核。

## 9. HTTP 200 还不是一次有效的 Agent 返回

在 `CONSULT-12__qwen_qwen3.5-27b__r3`，研究子 Agent 的一次 API 响应标记 `finish_reason=tool_calls`，但没有 `tool_calls` 列表，也没有正文。产品随后把 `None` 送进结果后处理，抛出类型异常。类似情况也出现在 19 和 21 的 Qwen 研究链路中。

这里需要区分两层：收到的模型/服务商协议异常，和产品没有在边界识别这个异常。不能只归因为“研究效果不好”，也不能把总控之后仍生成了答案当成整个研究流程成功。本轮没有隐藏这些失败；报告分别列出收到的异常响应、子 Agent 失败和最终任务是否结束。

下一轮应在模型返回边界检查“工具完成标志确实对应可执行调用、最终结果确实有正文”，给上层明确错误类型；再测试预算耗尽、工具禁用后的模型行为和有限次重试策略。问题来源还需进一步隔离模型输出与供应商响应转换，不能只凭这次记录把责任全部归给某一模型。

## 开会可以这样收尾

“我们完成的是一个可重复的开发测评基线，而不是单次漂亮演示。现在已经能把失败定位到五层：模型输出、提示词/调度、工具规则、记忆写入、测评器自身。下一轮每次只改一个明确问题，用相同病例、相同证据库和相同推理预算配对重跑。暂时没有实际接通的 Mem0 和微调医疗模型，明确保留为未验证项；没有前后对照的数据，就不编造提升比例。”
