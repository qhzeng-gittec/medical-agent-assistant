# Agent 关键设计与测评方法

本项目用一个总控 Agent（Supervisor）分派任务，由问诊、诊断、研究 Worker 调用工具并返回结果，再统一生成回答。工程设计主要解决五个问题：独立任务串行等待、检索证据不全、历史信息遗漏、重复证据占用上下文、模型超过工具预算。

每项设计均提供对照数据、样本量和测量方法，并链接原始记录，便于阅读与复核。

## 结果概览

| 设计 | 结果 | 证据类型与样本量 |
| --- | --- | --- |
| 独立任务条件并行 | 平均 49.80 → 20.15 秒，阶段耗时缩短 59.5% | 真实模型对照；同一组三个任务，串/并行各 3 次 |
| RAG 多候选 | 完整必需证据覆盖 33/40 → 39/40，+15 个百分点 | 检索组件对照；同一 40 个可回答问题，Top 1 对比 Top 3 |
| 主动历史补查 | Qwen、Gemini 四类信息覆盖 2/4 → 4/4；MiniMax 2/4 → 2/4 | 真实模型与受控历史池；1 个场景、3 模型、每配置 1 次 |
| 请求缓存与正文复用 | 同一 Worker 内 2 次相同请求 → 1 次底层执行 | 确定性组件测试；另检查重复正文变为引用 |
| 工具预算控制 | 161 次超预算提议全部拒绝，观察到的越预算执行为 0 | 277 组已完成运行的当前对话阶段审计 |

## 1. 条件并行：减少独立子任务的等待

总控在同一轮分派互不依赖的任务时，Worker 可以并发执行。评测固定同一组任务，直接比较串行和并行的批次耗时。

**测法：** 使用真实 MiniMax M2.5 和工具，固定诊断、问诊、研究三个任务，串行与并行各运行 3 次，交替执行顺序，期间不运行其他本次评测任务。计时从 Worker 批次开始到最后一个 Worker 返回，不包含总控规划和最终汇总。

| 指标 | 串行 | 并行 |
| --- | ---: | ---: |
| 三次耗时（秒） | 56.64、42.58、50.19 | 22.47、13.86、24.11 |
| 平均耗时（秒） | 49.80 | 20.15 |
| 最大实际 Worker 并发数 | 1 | 3 |

耗时缩短率 = `(串行均值 − 并行均值) / 串行均值`，结果为 **59.5%**；加速倍数 = `串行均值 / 并行均值`，为 **2.47 倍**。统计单位为 Worker 批次，取各模式 3 次实测均值；生成长度和云端负载随真实 API 请求变化。

完整流程包含总控规划、任务分派与汇总，另行统计单/多 Agent 的耗时和费用。[完整架构对照](architecture.md) · [机器汇总](agent/architecture_compare_20260908_v2/comparison_summary.json)

## 2. RAG 多候选：保留回答所需的不同证据

只取最相似的一段文档，可能覆盖问题的一部分。返回 Top 3 候选，让下游 Agent 同时看到多组相关证据。

**测法：** 固定 15 个来源文档块，来自 NHS/CDC 内容的中文摘要，含模型辅助整理、未经临床专家审核。查询与文档使用真实 `qwen/qwen3-embedding-8b` API 生成 4,096 维向量，在本地按余弦相似度排序。60 个检索探针中，下面使用 40 个可回答问题；其余用于无答案及上下文/过滤边界检查。

每题预标注“必需证据组”，同组可接受多个等价文档块。**完整覆盖**指每个必需组都至少命中一个可接受块；仅命中其中一组不算完整。固定同一排序、相似度阈值 0.0，只改变返回数量：

| 返回数量 | 至少命中一组 | 命中全部必需组 | 完整覆盖率 |
| --- | ---: | ---: | ---: |
| Top 1 | 40/40 | 33/40 | 82.5% |
| Top 3 | 40/40 | 39/40 | 97.5% |

Top 3 增加了 **6 个完整覆盖问题，提升 15 个百分点**。该指标衡量 15 文档本地索引上的完整证据覆盖，按原始标注统计；标签复核与最终回答评测各有独立记录。

候选召回与正文支持判断分别评测：检索负责提供相关材料，下游核对正文与来源。另附 12 个相近主题的无答案探针，用于分析相似度阈值与证据支持的关系。

## 3. 分层记忆：初始召回不足时主动补查

系统分别保存结构化患者档案、近期对话和可检索历史。总控发现信息缺口时，可以调用 `search_patient_history`，补充初始召回之外的记录。

**测法：** 固定一个五条记录的合成历史池，初始只返回前三条。用户要求整理四类信息：疾病、过敏、工作作息、运动限制。前三条包含疾病、过敏和已停用的药物；后两条包含每周交替日夜班、腰部旧伤及避免提重物的医嘱。因此初始召回只覆盖用户要求的 2/4 类。

| 被测模型 | 仅初始召回时覆盖 | 允许主动补查后覆盖 | 实际行为 |
| --- | ---: | ---: | --- |
| Qwen3.5-27B | 2/4 | 4/4 | 调用补查工具，回答包含两类遗漏历史 |
| Gemini 3.5 Flash | 2/4 | 4/4 | 调用补查工具，回答包含两类遗漏历史 |
| MiniMax M2.5 | 2/4 | 2/4 | 沿用初始召回的两类历史信息 |

覆盖按原始回答与工具轨迹逐项核对，以正确复述指定个人历史为准。**统计口径：单场景观察，每模型每配置 1 次；两配置包含多项系统设置差异。** 历史池按数量返回预设记录，用于观察主动补查决策；真实 Mem0 服务另行评测。

证据位于[结果附件](README.md)的 `agent/improvement_v2/runs/N08__*__baseline.json` 与 `N08__*__candidate.json`，其中 `turns[].answer` 是最终回答，`turns[].result.call_trace` 记录补查调用。通用运行逻辑见 [campaign_improvement.py](../../medix-agent-swarm/evals/campaign_improvement.py)。

## 4. 证据复用：减少重复执行和重复正文

这里有两个独立机制。相同工具与参数在同一次 Worker 调用内复用结果；不同查询返回同一文档时，首次注入正文，后续用指向首次工具结果的引用保留来源。

**测法：** 使用固定工具返回值，记录底层执行次数，并检查模型收到的工具消息。这类测试验证机制，不调用真实模型评分。

| 组件检查 | 观察结果 |
| --- | --- |
| 同一 Worker 内两次相同工具与参数，依次调用或并发调用 | 底层执行 1 次，缓存命中 1 次 |
| 两次不同查询 | 底层执行 2 次，不误用请求缓存 |
| 不同查询返回同一文档与版本，前文仍保留正文 | 第二次消息保留来源及引用，不重复正文 |
| 文档内容/版本变化，或前文正文已被裁剪 | 重新注入正文，避免留下无法解析的引用 |

结果验证了请求缓存、正文引用和内容更新时的重新注入。统计范围为一次 Worker 调用，指标是底层执行次数与消息内容；近期对话另通过长度预算控制上下文规模。

## 5. 工具边界：模型提议与实际执行分开

Worker 按角色获得工具，执行层限制工具调用预算。预算耗尽后，即使模型继续提出工具调用，也必须由执行层阻止。

**测法：** 对 277 组已完成运行的当前对话阶段做离线审计。逐个读取响应中的正式 `tool_calls`，与该次请求声明的工具列表比较，再按调用 ID、角色和工具名匹配实际执行结果。普通回答里的工具名称或伪调用文本不计入分母。

观察到 **161 次当轮未声明的工具提议**，都发生在同一 Worker 的工具预算耗尽之后；**161 次均返回 `ToolCallBudgetExceeded`，越预算执行为 0**。统计单位为工具提议，涉及 65 组运行、107 次 Worker 调用。历史预置阶段的记录另计。

本专项验证实际运行中的工具预算控制。档案写入采用相同的状态核对思路：根据工具返回和持久化状态判断保存结果。

## 整体系统怎么验收

以上专项分别测机制与局部效果。另有 72 个合成场景，覆盖问诊、历史记忆和证据使用，在三款真实模型上执行，逐轮核对回答、档案状态和工具证据。详细的样本构成、双评规则、完成数与通过数见 [整体验收方法与结果](agent_holdout.md)。

原始汇总与逐场景记录通过[数据索引与复算入口](README.md)访问。Agent 使用报告中标注的 API 模型，微调模型另行评测。本项目定位为研究与工程演示。
